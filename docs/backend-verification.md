# Hosted backend verification

Checked on 28 October 2026 using the existing Vercel-linked project. Disposable confirmed test accounts were created through the admin API, signed in using temporary passwords, and deleted after verification. No emails were sent. Keys, passwords and session tokens remained in subprocess memory and were not logged or written to application files.

- The frontend has both Supabase URL and publishable key configured. The existing `user_state` payload model can store the new exam-scoped version3 JSON without a table migration.
- The project was initially paused: the configured host returned NXDOMAIN. After the user resumed it, DNS and HTTPS recovered. The existing `public.user_state` table, its four expected columns, enabled RLS and three owner policies were verified through the authenticated management connection. A PostgREST schema-cache reload resolved the transient **404 / PGRST205**. No initialization migration or replacement database was needed.
- `/auth/v1/health` with the configured publishable key returns **200** (`GoTrue`, version `v2.197.0`). `/auth/v1/settings` returns **200** with **Google and email enabled**. These checks confirm the existing configured project is reachable and those providers are enabled; they do not complete a user's OAuth login.
- Two synthetic users each inserted their own progress row, reloaded an exact payload match, upserted a changed payload on `user_id`, and reloaded the updated result. Both AP SI and NICL namespaces survived the roundtrip in the same version3 payload.
- A second user's read of the first user's row returned **200 with an empty result**. Its attempted update returned **200 with zero affected rows**, and the original owner's data remained unchanged. Its insert using the other user's ID returned **403 / PostgreSQL 42501**. These are live per-user isolation checks, not only SQL inspection.
- Anonymous reads returned **200 with an empty result** and anonymous inserts returned **401**. Real candidate rows were not read, changed or deleted.
- Cleanup returned **204** for each synthetic row and **200** for each synthetic user deletion. A final exact-ID check found **zero remaining synthetic rows**. The same authenticated insert/upsert/reload and isolation checks also passed against Saapadu's existing `user_backups` table; its anonymous reads and writes returned **401**.

Google authorize requests using the exact web origin `https://lakshya-ap-si-prep.vercel.app` and native callback `com.tpavan.lakshya://login-callback` each returned **302 to `accounts.google.com`**, without following the redirect or signing into Google. The returned OAuth state was opaque, so these checks confirm provider initiation but do not independently prove the final redirect allowlist accepted the requested callback.

These results verify the hosted REST persistence and access-control path with actual authenticated sessions. They do not claim a human completed Google sign-in, that native OAuth returned on a physical Android device, or that two physical devices were used. Device-only preparation and JSON backups remain available independently of cloud service availability.

The sync hook now gates writes until the current account’s hydration succeeds, rejects stale results from earlier accounts, keeps separate local account caches, preserves work across same-account token refreshes, serializes writes, and retries failed hydration through **Sync now**. Unknown legacy local ownership is not copied into a newly restored account. Existing cloud rows remain authoritative; guest work can seed an empty row only after explicit sign-in, and a previous account’s data can never seed another account.

Initialization, hydration and writes are bounded to 12 seconds so an unreachable backend cannot leave the app indefinitely on its restoration screen. Native callback handling validates the registered scheme and host. AP and NICL progress use the same per-user backend row, with separate exam namespaces inside its payload. Google/email sign-in also checks backend health before starting, so restored service becomes available without a hardcoded outage switch.
